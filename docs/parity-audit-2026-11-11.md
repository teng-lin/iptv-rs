# TiviMate functionality parity audit — 2026-11-11

The current iptv-rs implementation covers much of the **live-TV core**, but it is **not full TiviMate Premium parity**. The largest absent user journeys are recording, reminders, saved programmes/watchlists, VOD browsing/resume, parental controls, complete backup/restore and SMB storage. Important live-TV gaps remain in channel/group editing, editable remote mappings, configuration breadth and multiview capacity.

## Scope and interpretation

This is an independent source-and-test audit, not a rewrite of the product plan or an implementation task. Starting checkout: **12dc1a39e81fa1a40b1807f1e366554e6e476e62**, clean at inspection start. Repository changes from this audit are documentation only. Test logs and the machine-readable matrix are under `/home/blackmyth/analysis/iptv-rs-parity/2026-11-11/`. No emulator, physical tablet, real provider or private credentials were accessed. Builds used one Cargo job to limit resource pressure.

Reference evidence, strongest first:

1. Existing controlled TiviMate runtime findings: [R9 menus/past programmes](../../tivimate/docs/08-menus-and-past-programmes.md), [Premium entry-point investigation](../../tivimate/docs/09-premium-and-library-features.md), and the [Premium multiview report](/home/blackmyth/analysis/tivimate-runtime/multiview/REPORT.md). The earlier unactivated gates limit some reference conclusions; they do not prove a feature is absent from Premium.
2. APK declarations/REA/IDA analysis: [functional specification](../../tivimate/docs/01-functional-specification.md), [settings reference](../../tivimate/docs/03-settings-reference.md), and [static guide-style audit](/home/blackmyth/analysis/tivimate-runtime/guide-style/REPORT.md). A declaration establishes a capability family, not every runtime detail.
3. The third-party [analysis index](../../TiVIMate_Analysis/README.md) supplies feature leads. Its architecture, timings, palette and synthetic decompiler names are not accepted as proof. Concrete mismatched resource-ID claims were already demonstrated in the guide-style audit.

**Implemented** means a reachable app path and supporting code exist; it does not certify all hosts or exact TiviMate semantics. **Partial** means some important behavior/configuration is absent. **Backend only** means types/storage/algorithms exist without a complete user journey. **Missing** means no usable feature was established from the inspected entry points. **Different** is an observable policy difference, which may be intentional. **Excluded** is deliberately unavailable in this product scope, still a gap against full reference coverage. **Reference unknown** means the comparison cannot be established even if iptv-rs has implementation.

There is no defensible single percentage: feature sizes differ, several reference behaviors remain unknown, and unit/headless tests do not establish native device playback. The following finite matrix is the audit boundary, not every TiviMate setting or provider variant.

## Findings that change the existing parity assessment

- **Four screens versus nine is a real capacity gap.** `MAX_SURFACES` and the app's player-surface contract currently stop at four. A layout helper capable of calculating three-column positions does not make a fifth decoder/player reachable. “Multiview done” in the existing parity document is therefore too broad.
- **Guide history is intentionally stricter than the captured reference.** Focus on channels without catch-up is lifted to now, and the scroll range uses catch-up retention. The reference R9 feed showed old programmes even without archive playback. Browsability and playability need separate policies if exact reference behavior is desired.
- **Menu rows and catalogue entries overstate functionality if counted mechanically.** The guide action gate enables only Search, Settings, Description, ToggleFavorite, StartFromBeginning, ManageFavorites and AssignEpg. A `Record`/`Reminder`/`CreateGroup` enum variant is not a working feature. Likewise, `remote.customize` runs a command but opens a read-only key list.
- **Playlist/settings status is internally inconsistent in the older document.** Its navigation table still says the Settings/Playlists entries do nothing and playlist support is missing, while its later section correctly describes their working screens. Current source supports the latter. Its “no channel list” wording also needs separation between the implemented player list and a general guide-list preference.
- **Storage is ahead of UI.** Rename/hide/block/manual order/custom groups and richer provider identities have data structures or persistence APIs. The end-user handlers, workflow rules and enforcement remain incomplete. The same distinction applies to settings backup JSON versus whole-app backup/restore.
- **Provider-builder tests do not certify TiviMate request parity.** M3U builders document IPTV Simple behavior. Xtream variant probing is not yet implemented; portal archives are unsupported. The prior mock TiviMate run hit Premium before emitting archive URLs, so its configured templates are not observed app requests. A future synthetic Premium request capture would resolve that boundary.
- **Platform exclusions are product decisions.** AFR/passthrough/decoder choice/boot behavior/voice search/self-update may be sensible omissions for a portable MVP. They must still be listed when claiming full Android-TV feature parity. Desktop/iPad pointer controls and custom PiP are valuable additions, but do not compensate numerically for missing TV features.

## Priorities

This ordering respects the repository's live-TV MVP focus; it does not silently promote all deferred Premium features to immediate requirements.

| Stage | Concrete work | Acceptance boundary |
| --- | --- | --- |
| Live-TV completeness | Expose channel/group rename, hide and reorder; custom groups/copy; per-playlist enablement/configuration; editable remote mappings | User can complete, cancel and persist the journey across restart and playlist refresh; identity-based focus and overrides survive |
| Existing-feature parity | Raise multiview capacity where supported, with a device/decoder cap; separate past-guide browsing from replay permission; explicitly decide Back/Menu/one-tile-menu differences | Synthetic 1–9 tile tests, host player lifecycle/audio checks, and old no-catch-up programme navigation without enabling playback |
| Configuration and reliability | Wire the promised appearance/history/buffer/stay controls or keep them clearly unavailable; test track/audio-delay/PiP/background behavior on each host | Persisted setting demonstrably changes behavior; unsupported host feature is capability-gated; native smoke tests, not compilation alone |
| Full Premium journeys | Recording/schedules/library/storage; reminders and delivery; watchlist; VOD catalogue/details/resume/episodes; parental PIN/enforcement | End-to-end synthetic flows with restart, failure, cancellation and permission/lifecycle cases |
| Portability/operations | Complete whole-app export/restore and SMB; localization; choose explicitly which TV hardware and maintenance features to support | Replacement/rollback and secret handling verified; no borrowed app assets or branded activation flow |

Do not implement a third-party claim of Canvas rendering, a 90-minute cache, a 250MB logo cache, a 150ms focus zoom or a particular database layout merely to obtain “parity.” Observable user behavior and measured performance are the requirements; implementation internals can differ.

### Remaining reference verification

For narrower parity claims, use synthetic Premium runtime comparisons for M3U/Xtream archive request patterns, remote repeats/remapping, guide navigation without catch-up, full multiview 1–9 behavior and native audio/decoder limits. The existing captured multi-tile Back result is scoped to one configured tablet and must not become a universal default. Protected static code and the third-party write-up do not settle those questions.
